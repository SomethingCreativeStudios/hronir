# Hrönir

<img src="hronir-icon.svg" align="left" width="80" height="85" hspace="20" vspace="10" alt="Hrönir icon">

*hrönir (pronounced "HRUH-neer"), from Borges's "Tlön, Uqbar, Orbis Tertius": objects produced by the act of searching for them, never quite identical to the original, shaped by the finder's expectations.*

Hrönir is a harvester written in Go. It crawls OGC API Connected Systems servers, transforms their resources into OGC API Records, and delivers them to a catalog such as [tlon](https://github.com/SomethingCreativeStudios/tlon).

<br clear="left">


## Why

Getting Connected Systems resources into a catalog takes more than copying them. Systems arrive as GeoJSON or SensorML, vocabularies differ between deployments, and a useful discovery record needs titles, keywords, themes, and extents that the source often only implies. Hrönir produces a derived representation shaped for discovery rather than a mirror of the source, which is what the name means.

Because it only speaks the CS API, Hrönir works against any conformant server, including servers you don't control and could never get database access to.

# What is it, really?

- ingests Connected Systems Systems (including subsystems), Deployments, Procedures, Sampling Features, Properties, Datastreams, and Control Streams, with Observations, commands, command status/results, and event/history instances intentionally out of scope;
- prefers SensorML for Systems, Deployments, Procedures, and Properties, GeoJSON for Sampling Features, and JSON for streams, follows `rel=next` links, and treats an incomplete crawl as ineligible for deletion;
- maps each resource kind through an embedded `connected-systems/v1` typed profile, with per-field RFC 9535 JSONPath and pipe-function expressions, optional local JavaScript functions, and schema/queryable/facet declarations for any added field;
- writes deterministic UUIDv5 record IDs to the target with unconditional PUT create/replace and idempotent DELETE, against catalogs that advertise `supportsNonAutogeneratedResourceIds`;
- authenticates sources and targets with a Bearer secret reference, OAuth2 client credentials, or mTLS, with secrets always passed by reference, never by value;
- tracks state in SQLite (WAL plus an exclusive process lock), hashes semantic Records to skip no-op writes, preserves the last known good Record on mapping/write failure, and mark/sweep-deletes only after a complete crawl of a source/kind;
- accelerates polling with MQTT discovered from `/asyncapi`, treating only regular CloudEvents lifecycle channels as a hint that a resource changed rather than as the authority on its state;
- runs continuously with `/healthz`, `/readyz`, and Prometheus `/metrics`, in a distroless production image that runs as UID 65532.

## Quick start with Tlon

```sh
cp examples/hronir.yaml hronir.yaml
go run ./cmd/hronir config validate -c hronir.yaml
go run ./cmd/hronir catalog render -c hronir.yaml --format tlon > connected-systems.json
tlon catalog apply connected-systems.json
go run ./cmd/hronir sync -c hronir.yaml
```

The target collection must exist and advertise
`supportsNonAutogeneratedResourceIds: true`. Hronir uses deterministic UUIDv5
record IDs, unconditional PUT create/replace, and idempotent DELETE.

Run continuously with `hronir run`. It serves `/healthz`, `/readyz`, and
Prometheus metrics at `/metrics` on `runtime.listenAddress`.

The production image runs as UID 65532. Mount `/data` with write permission for
that UID; the included Compose stack uses a one-shot initializer for its named
development volume.

## Configuration

Configuration is strict YAML (`apiVersion: hronir.io/v1alpha1`,
`kind: Harvester`). See [examples/hronir.yaml](examples/hronir.yaml).

Each source has a stable `id`; changing it intentionally creates a new identity
space. Resource modes are `auto` (default), `required`, and `disabled`.
Hronir prefers SensorML for Systems, Deployments, Procedures, and Properties;
Sampling Features use GeoJSON; streams use JSON. It follows `rel=next` links
and treats incomplete crawls as ineligible for deletion.

HTTP source and target authentication supports a Bearer secret reference,
OAuth2 client credentials, and mTLS. Secrets are references only:

```yaml
auth:
  bearer: {env: CS_TOKEN}
# or
auth:
  oauth2:
    tokenUrl: https://identity.example/token
    clientId: hronir
    clientSecret: {file: /run/secrets/hronir-client-secret}
```

## Mappings

`connected-systems/v1` is an embedded typed profile. Mapping expressions start
with `=` and use RFC 9535 JSONPath followed by pipe functions:

```yaml
mapping:
  overlays:
    systems:
      fields:
        /properties/title: '= $.name | trim | default($.uid)'
        /properties/connectedSystems/region:
          expr: '= $.metadata.region | upper'
          schema: {type: string}
          queryable: true
          sortable: false
          facet: true
```

Existing profile fields may be overridden with an expression. A new field must
declare schema and query/facet flags so `catalog render` can make a compatible
Tlon bundle. Use YAML `null` to remove a built-in field. Local JavaScript
functions register a namespaced pure function; see
[examples/functions](examples/functions).

```sh
hronir mapping test -c hronir.yaml --kind systems --input examples/canonical-system.json
```

## Synchronization safety

Hronir stores state in SQLite (WAL plus an exclusive process lock). It caches
normalized resources, hashes semantic Records to avoid no-op writes, preserves
the last known good Record on mapping/write failures, and performs mark/sweep
only after a complete source-kind crawl. The default deletion threshold is two
complete misses. `hronir remap` reuses the cache; `hronir prune --source ...
--kind ... --yes` is the only command that deliberately removes a source/kind.

MQTT is discovered from `/asyncapi` unless broker/topics are configured. Only
regular CloudEvents lifecycle channels are accepted; Resource Data Messages and
Batch Events are ignored. Each accepted event fetches its subject before any
target action, so events accelerate polling rather than becoming the authority.
The current Connected Systems MQTT binding is treated as discovered runtime
compatibility, not as a claim of formal Part 3 MQTT conformance.

## Development

```sh
make check
make race
make build
```

Go automatically obtains the configured Go 1.27 toolchain when needed.

For a local Tlon, Mosquitto, and deterministic Connected Systems fixture, run:

```sh
docker compose up --build --wait
curl http://localhost:8081/readyz
curl 'http://localhost:8080/collections/connected-systems/items?limit=20'
docker compose down -v
```
